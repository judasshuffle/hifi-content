# ROBOTDOLLY Theatre MK2

MK2 is an **unverified prototype** for DarkRide 1.1 beta. It does not alter MK1. The recording library and shared-worker mode have only been tested with mocks, not in DarkRide. The existing MK1 server-side actor and a prior numbered MK2 Actor 1 have been reported working; do not infer five-actor, upload, logout or restart behavior from those results.

## Architecture and assignment

The managed `-t 2 --max 5` process supplies at most five agent workers; it does not itself request five scripts. For shared-worker mode, configure **one persistent `worker.js` URL** with the desired number of copies. Each copy loads `actor.js` and obtains a slot from the show entity coordinator. The workers reserve type-2 capacity even while idle; this is not dynamic allocation. With MK1 running and no other agents, at most four MK2 copies can run. The coordinator waits 12 seconds after startup before issuing leases; workers stop their script if renewal is lost for 8 seconds. A restarted worker may claim a different slot, and an individual worker restart does not automatically reapply its show settings. Timing, recovery and duplicate prevention are not proven on the live server.

The earlier `actor-1.js` through `actor-5.js` wrappers remain available for numbered installations. **Do not run numbered wrappers and shared workers on the same MK2 channel**: the coordinator cannot reserve wrapper slots, so two agents could accept the same commands. Do not run more than one show coordinator on a channel.

`show-server.js` is a server entity script, not a sixth agent. It stores one show in the persistent domain entity's `userData` and optionally sends configuration/play commands after startup. This uses domain entity storage, not viewer Settings or operator-local files. The HUD is a viewer script. Closing the HUD does not send stop commands. Continuing after logout depends on the domain retaining the assignments and is not yet verified.

## Installation for a controlled test (do not install on a live show)

1. Copy the MK2 directory to a script host accessible to the domain and viewers, preserving its directory structure. `worker.js` resolves `actor.js` relative to its URL. Host `worker.js`, `actor.js`, `show-server.js`, and `theatre-hud.js`. Verify the server can fetch every file and HFR asset; local viewer filesystem paths are not sufficient for server agents.
2. The scripts use a public GreatATuin test channel and marker (`PUBLIC-GREATATUIN-MK2-TEST-V1`) consistently. This is only an accidental-crosstalk filter, **not authentication or a secret**. Anyone able to read these scripts and send domain messages can control actors and overwrite the show. Use a trusted test domain and appropriate domain permissions; do not treat this as secure multi-user administration or put credentials in these files.
3. In domain settings, register `worker.js` once with **two copies**, using the pool matched by the existing type-2 process. Ensure capacity is free and remove any earlier MK2 numbered assignments before starting shared workers; preserve MK1. Verify two distinct agents receive separate recordings, play concurrently, and keep playing independently when one is stopped or changed. `Check Actors` reports responses but cannot detect duplicate assignments. The coordinator must be installed as in step 4 before workers obtain slots.
4. Create one persistent domain entity and attach the hosted `show-server.js` as its server script. Retain the entity ID and back up its `userData`. The server script must have permission to edit this entity and access Messages. Use exactly one MK2 show entity per domain/channel. Verify Save Show reports success and the entity's `userData.robotdollyMK2` survives an entity-server restart before relying on it. Save acknowledgement is a delayed read-back, not confirmation that the entity database has flushed to durable storage.
5. Run `theatre-hud.js` in the viewer. Under RECORD, start and stop a new recording, then select **Save Recording** and enter a unique name. The viewer uploads its last recording through `Recording.saveRecordingToAsset`, maps its hash to a `.hfr` path with `Assets.setMapping`, then requests a server-library entry. Asset upload and mapping permissions are required. Upload, mapping, server entity editing and read-back must all work; failure is shown in the HUD. A successful mapping with failed library registration can leave an orphaned ATP asset, and its URL is shown on registration failure. Uploading and mapping have not been verified on DarkRide. No recordings are preloaded or imported.

   Under CAST, select an actor and use **Recording Library** to open the list and select a saved recording, or use **Load URL** for an existing recording. Choose placement and volume, then play. Select and configure the other actor independently. The persistent entity stores library names, ATP URLs, creation times, format and recorded duration. A case-insensitive duplicate name is rejected. Asset mapping and entity data should be backed up. Save Show stores the actor slots, loops and volumes separately; saving a show does not import recordings into the library. Load Show applies saved settings and stops/reloads configured actors; Play All starts configured slots.
6. Test on a non-production domain. First test the two-actor case; extend to five only after it passes. Close the operator viewer while a second observer verifies continued movement and speech. To test recovery, save with Restore on restart enabled, then perform an authorized test domain restart and verify each actor's identity, recording, location, volume and loop from another viewer. No restart is performed by these scripts. Restore starts all saved configured actors whether or not they were playing when saved. It probes agents for up to one minute, then sends each responding slot its settings and play command. Late agents, lost messages and failed loads can leave a partial show; it is not a reliable recovery guarantee. Disable the option until tested and use Load Show / Play All for manual recovery.

## Placement and audio

Original Recorded Location uses `Recording.setPlayFromCurrentLocation(false)`. In the inspected local DarkRide source, `AvatarData::toJson` records a basis and a relative avatar transform, and `AvatarData::fromJson` reconstructs world position and orientation from that basis; `Agent.cpp` sets a new basis only for current-location playback and clears it when playback stops. This supports replay at the recorded basis for compatible HFR frames. It does not establish bit-for-bit accuracy, cover every legacy HFR, or verify the deployed image matches this source. Compare a known recording's position, path and orientation on the actual server. Here, In Front of Me and Custom Coordinates set the starting position; the agent's current orientation is the playback basis, so relative-path orientation should be checked on the target build.

Audio stays inside the HFR and is played by each server agent; there is no separate viewer-side WAV injection. The inspected local agent source applies the Recording player's volume to HFR audio frames. Actor volume ranges from 0–100%; it is independent per process. Audio depends on the deployed assignment-client having the working HFR audio implementation and on recording format, mixer, and network behavior. Confirm speech and volume in the actual beta image. `setPlayerUseSkeletonModel(false)` is not supported in the inspected agent source, so the HFR's recorded avatar model may be used; check asset availability.

The inspected viewer implementation uploads `Clip::toBuffer(_lastClip)` directly, rather than converting or extracting audio or movement. Its recording API and resource loader support ATP URLs in the inspected source; agent access to mapped HFRs, permissions, full audio and movement preservation, and the actual deployed viewer/server versions still need an end-to-end test. The library and show use the same entity `userData`; read-back is not a durable-flush guarantee. Use one coordinator and one operator during testing. Simultaneous edits from other scripts or users are not transactionally protected.

Loop Show sets the loop flag on all configured actors; it does not synchronize different-duration clips or restart them together at a common boundary. Play All is sequential message dispatch, not frame-synchronized playback. Unacknowledged network messages, failed loads, assignment restarts, changes by other operators, and late agents can leave a partial show. The HUD status is the last reported message, not a health guarantee; Check Actors requests fresh responses. Recording APIs are experimental and save is asynchronous. Upload saved HFR files to a server-accessible URL separately.

## Local checks and rollback

Run `node robotdolly-hfr/mk2/test-mk2.js`, `node robotdolly-hfr/mk2/test-library.js` and `node --check` on the scripts. The tests simulate independent agents, asynchronous loads, messages, library uploads and failures, worker leases and server-entity storage. They do not simulate DarkRide's networking, ATP, audio, database, HFR decoder, pool scheduling or entity permissions.

For rollback, stop the MK2 actors via the HUD, remove only the MK2 persistent worker or numbered assignments, and detach or remove the dedicated MK2 show entity after backing up its data. Stop the MK2 viewer HUD. Back up ATP mappings and files before removing any library assets. Restore prior server settings as appropriate. Do not remove or change MK1 scripts or assignments. Follow normal domain administration procedures for any required setting reload; this repository does not make server changes.
