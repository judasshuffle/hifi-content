# ROBOTDOLLY Theatre MK2

MK2 is an **unverified prototype** for DarkRide 1.1 beta. It does not alter MK1. The recording library and shared-worker mode have only been tested with mocks, not in DarkRide. The existing MK1 server-side actor and a prior numbered MK2 Actor 1 have been reported working; do not infer five-actor, upload, logout or restart behavior from those results.

## Architecture and assignment

The managed `-t 2 --max 5` process supplies at most five agent workers; it does not itself request five scripts. For shared-worker mode, configure **one persistent `worker.js` URL** with the desired number of copies. Each copy loads `actor.js` and obtains a slot from the show entity coordinator. The workers reserve type-2 capacity even while idle; this is not dynamic allocation. With MK1 running and no other agents, at most four MK2 copies can run. The coordinator waits 12 seconds after startup before issuing leases; workers stop their script if renewal is lost for 8 seconds. A restarted worker may claim a different slot, and an individual worker restart does not automatically reapply its show settings. Timing, recovery and duplicate prevention are not proven on the live server.

The earlier `actor-1.js` through `actor-5.js` wrappers remain available for numbered installations. **Do not run numbered wrappers and shared workers on the same MK2 channel**: the coordinator cannot reserve wrapper slots, so two agents could accept the same commands. Do not run more than one show coordinator on a channel.

`show-server.js` is a server entity script, not a sixth agent. It stores one show in the persistent domain entity's `userData` and optionally sends configuration/play commands after startup. This uses domain entity storage, not viewer Settings or operator-local files. The HUD is a viewer script. Closing the HUD does not send stop commands. Continuing after logout depends on the domain retaining the assignments and is not yet verified.

## Installation for a controlled test (do not install on a live show)

1. Host `worker.js`, `actor.js`, `show-server.js`, and `theatre-hud.js` in the same directory, accessible to domain and viewer. The GitHub branch base is `https://raw.githubusercontent.com/judasshuffle/hifi-content/feature/robotdolly-theatre-mk2/robotdolly-hfr/mk2/`; append the filename. `worker.js` resolves `actor.js` relative to its own URL. GitHub raw availability does not establish that GreatATuin can reach the files.
2. The scripts use a public GreatATuin test channel and marker (`PUBLIC-GREATATUIN-MK2-TEST-V1`) consistently. This is only an accidental-crosstalk filter, **not authentication or a secret**. Anyone able to read these scripts and send domain messages can control actors and overwrite the show. Use a trusted test domain and appropriate domain permissions; do not treat this as secure multi-user administration or put credentials in these files.
3. Before migrating, record the existing domain settings and any MK2 entity ID and `userData`. Stop older MK2 actors with their HUD. Remove only the older MK2 numbered assignment rows (`actor-1.js` etc.), preserving the MK1 `ROBOTDOLLY_Actor_Server.js` row. Apply changes using the domain's normal administration procedure and **verify the old MK2 agent instances have actually exited** before proceeding; removing a settings row is not proof that a running agent stopped. If the domain requires a restart or the old instances remain, stop and schedule a separate authorized maintenance action. Never run numbered and shared MK2 workers together.
4. Reuse the existing MK2 show entity if one was created; otherwise create one persistent domain entity. Back up its `userData`, attach the current hosted `show-server.js` as its server script, and verify that the current version actually loaded. The server script must have permission to edit this entity and access Messages. Use exactly one MK2 show entity per channel. Entity script caching or reload requirements depend on the deployment. Save acknowledgement is a delayed read-back, not confirmation that the entity database has flushed to durable storage.
5. In domain settings, add the `worker.js` URL once with **two copies** and a blank runner group, matching the described GreatATuin pool. Preserve all MK1 rows. Apply using normal domain procedures and check that two separate new worker assignments are running. Workers need the coordinator and can take over 12 seconds to claim slots. Confirm Actor 1 and Actor 2 respond to **Check Actors**; this does not detect duplicates. If rows are not applied without a restart, stop and arrange a separately authorized maintenance action.
6. Run `theatre-hud.js` in the viewer. Under RECORD, start and stop a new recording, then select **Save Recording** and enter a unique name. The viewer uploads its last recording through `Recording.saveRecordingToAsset`, maps its hash to a `.hfr` path with `Assets.setMapping`, then requests a server-library entry. Asset upload and mapping permissions are required. Upload, mapping, server entity editing and read-back must all work; failure is shown in the HUD. A successful mapping with failed library registration can leave an orphaned ATP asset, and its URL is shown on registration failure or timeout. Uploading and mapping have not been verified on DarkRide. No recordings are preloaded or imported.

   Under CAST, select an actor and use **Recording Library** to open the list and select a saved recording, or use **Load URL** for an existing recording. Choose placement and volume, then play. Select and configure the other actor independently. The persistent entity stores library names, ATP URLs, creation times, format and recorded duration. A case-insensitive duplicate name is rejected. Asset mapping and entity data should be backed up. Save Show stores the actor slots, loops and volumes separately; saving a show does not import recordings into the library. Load Show applies saved settings and stops/reloads configured actors; Play All starts configured slots.
7. Test on a non-production domain. First test the two-actor case; extend only within available capacity. Close the operator viewer while a second observer verifies continued movement and speech. To test recovery, save with Restore on restart enabled, then perform an authorized test domain restart and verify each actor's identity, recording, location, volume and loop from another viewer. No restart is performed by these scripts. Restore starts all saved configured actors whether or not they were playing when saved. It probes agents for up to one minute, then sends each responding slot its settings and play command. Late agents, lost messages and failed loads can leave a partial show; it is not a reliable recovery guarantee. Disable the option until tested and use Load Show / Play All for manual recovery.

## Placement and audio

Original Recorded Location uses `Recording.setPlayFromCurrentLocation(false)`. In the inspected local DarkRide source, `AvatarData::toJson` records a basis and a relative avatar transform, and `AvatarData::fromJson` reconstructs world position and orientation from that basis; `Agent.cpp` sets a new basis only for current-location playback and clears it when playback stops. This supports replay at the recorded basis for compatible HFR frames. It does not establish bit-for-bit accuracy, cover every legacy HFR, or verify the deployed image matches this source. Compare a known recording's position, path and orientation on the actual server. Here, In Front of Me and Custom Coordinates set the starting position; the agent's current orientation is the playback basis, so relative-path orientation should be checked on the target build.

Audio stays inside the HFR and is played by each server agent; there is no separate viewer-side WAV injection. The inspected local agent source applies the Recording player's volume to HFR audio frames. Actor volume ranges from 0–100%; it is independent per process. Audio depends on the deployed assignment-client having the working HFR audio implementation and on recording format, mixer, and network behavior. Confirm speech and volume in the actual beta image.

The HUD captures `MyAvatar.skeletonModelURL` when a recording starts and stores it with that recording. It does not substitute the current viewer's model later. On playback, the actor applies a stored ATP or HTTP(S) model URL and clears prior attachments; missing, legacy, or local-only references are reset rather than replaced with the operator's avatar. It enables use of the HFR's own recorded model and appearance frames. The inspected agent code always applies frame model data, so the HFR can override the metadata model, particularly if the avatar changed during recording. The viewer source records avatar-entity data and the agent source reads recorded entities, but restoration of wearables, materials and complete appearance has not been verified. URLs must be accessible to the agent; `file:` and other local-only model references cannot be loaded by it. Existing library entries have no captured metadata and manual URLs rely on the HFR's embedded model.

The inspected viewer implementation uploads `Clip::toBuffer(_lastClip)` directly, rather than converting or extracting audio or movement. Its recording API and resource loader support ATP URLs in the inspected source; agent access to mapped HFRs, permissions, full audio and movement preservation, and the actual deployed viewer/server versions still need an end-to-end test. The library and show use the same entity `userData`; read-back is not a durable-flush guarantee. Use one coordinator and one operator during testing. Simultaneous edits from other scripts or users are not transactionally protected.

Loop Show sets the loop flag on all configured actors; it does not synchronize different-duration clips or restart them together at a common boundary. Play All is sequential message dispatch, not frame-synchronized playback. Unacknowledged network messages, failed loads, assignment restarts, changes by other operators, and late agents can leave a partial show. The HUD status is the last reported message, not a health guarantee; Check Actors requests fresh responses. Recording APIs are experimental and save is asynchronous.

## Local checks and rollback

Run `node robotdolly-hfr/mk2/test-mk2.js`, `node robotdolly-hfr/mk2/test-library.js` and `node --check` on the scripts. The tests simulate independent agents, asynchronous loads, messages, library uploads and failures, worker leases and server-entity storage. They do not simulate DarkRide's networking, ATP, audio, database, HFR decoder, pool scheduling or entity permissions.

For rollback, stop the MK2 actors via the HUD, remove only the MK2 persistent worker or numbered assignments, and detach or remove the dedicated MK2 show entity after backing up its data. Stop the MK2 viewer HUD. Back up ATP mappings and files before removing any library assets. Restore prior server settings as appropriate. Do not remove or change MK1 scripts or assignments. Follow normal domain administration procedures for any required setting reload; this repository does not make server changes.
