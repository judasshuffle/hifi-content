# Automatic agents: investigation

Status: the requested on-demand allocator is **not implemented**. This investigation is based on local DarkRide source trees `C:/Projects/darkride-hfr-playback` and `C:/Projects/darkride-release-10-18`. The precise source revision in GreatATuin's `darkride-synology:1.1-beta-theatre-multi` image has not been confirmed. No request was sent to GreatATuin and no server configuration was changed.

## Existing mechanisms

* `DomainServer::populateStaticScriptedAssignmentsFromSettings` creates one static agent assignment per configured script copy. A pool process supplies workers; `--max 5` is not a command to create five performer assignments.
* The domain's administrative `POST /assignment` accepts multipart JavaScript, optional `ASSIGNMENT-INSTANCES` and `ASSIGNMENT-POOL` headers, and enqueues an ephemeral agent assignment. `XMLHttpRequest` is available to assignment and server entity scripts, so an authenticated HTTP request is conceivable. This is an administrative interface, not a dedicated in-world spawn API. It is protected by the domain's configured web authentication; exposing or embedding admin credentials in publicly hosted scripts is unacceptable.
* The POST response is an empty HTTP 200: it does not return the new assignment ID or report available pool capacity. `GET /assignments.json` shows fulfilled and queued assignments, but cannot by itself reliably correlate an anonymous new POST to a caller during concurrent activity. Queued entries expose type and pool, not the submitted script or application lease.
* The inspected delete handler offers deletion of connected nodes and backups; it does not offer deletion of a queued assignment. Deleting a connected node is not the same as cancelling an unfulfilled assignment. A script that has started could potentially end itself, but persistent assignments are requeued, and cancellation before an ephemeral assignment starts remains unresolved. `Script.stop` documentation warns that assignment scripts may restart; exact behavior needs testing for ephemeral assignments on the deployed build.
* The pool's configured process limit is not returned by the assignment POST or established from the scripts. A queued assignment could mean a full pool, a disconnected worker, pool mismatch, authentication failure elsewhere, or another startup problem. A timeout must not be reported as proven pool fullness.

These gaps prevent a robust implementation of allocate, cancel and release with truthful full-pool feedback using only the inspected APIs. A design could attempt HTTP uploads with unique startup leases and have stale agents exit when eventually started, but that does not remove the stale queued assignments and can consume future capacity. There is no demonstrated safe place to supply privileged web credentials to a public script, or guarantee of correct behavior across controller restarts. No such workaround has been added.

## Capacity and practical alternative

One MK1 assignment plus five concurrent MK2 performers requires **six** agent workers. With the present `--max 5`, at most four MK2 performers can run alongside MK1, assuming no other agent assignments. An additional controller implemented as an agent would consume another worker; an entity server script does not consume a type-2 agent slot, although its reliability and permissions require live verification. Supporting five MK2 performers alongside MK1 requires additional capacity or stopping an existing agent; neither change has been made.

The smallest configuration change that avoids five distinct script entries would be one persistent worker script configured with multiple copies, with new code to claim distinct logical actor slots and report leases to the existing entity controller. This is a **proposed design, not an existing feature**: the current `actor.js` depends on an explicitly numbered wrapper and cannot safely be registered as multiple copies. It would reserve workers while idle rather than dynamically return them to the pool. Slot claiming, duplicate handling, crash recovery, show restoration and audio must be implemented and tested before recommending it. With MK1 left running on the current pool, configure at most four copies.

For true on-demand allocation and release, a future server-side extension or trusted local service should expose a narrowly authorized operation that creates a uniquely identified assignment, cancels it even while queued, releases a running worker without affecting MK1, and reports queue and capacity state. It also needs durable desired-show state, idempotent requests and restart reconciliation. Such a service would require separate installation and careful authentication; it is not an existing DarkRide scripting API and has not been built.

The current MK2 installation remains the separately numbered assignments documented in README.md. No implementation change has been made to MK1 or MK2 playback.
